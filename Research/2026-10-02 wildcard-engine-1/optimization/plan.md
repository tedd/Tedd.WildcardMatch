# Second investigation: committed direct engine

Baseline: 4bc779e, SDK 11.0.100-rc.1.26425.128, timed .NET 10.0.12. This continuation extends the original report; old Regex comparisons remain in their original epoch. No consuming application is supplied, so claims concern complete library calls, not application throughput.

Objective: reduce complete static/reused matching latency while preserving all tested Regex semantics, zero default match allocation and constructor cost. Equal importance for the original thirteen fixtures; additional losing distributions cover question runs, star retries, ASCII folding, long fixed runs, repeated stars and newline rejection. Retain only repeatable gains across launches without material credible regressions in ordinary short calls. Assess added branches/duplication/preparation proportionately. Small noisy movements are inconclusive, not improvements.

Control and candidate are built together as distinct assemblies from identical committed source, except the named transformation. The calibrated existing harness is extended to compare direct engines. Preserve common counts, observable checksums, ABBA/BAAB ordering, three fresh processes and all samples. Screening uses four blocks and >=5ms control calibration; acceptance uses nine blocks and >=20ms. Every candidate passes the independent exhaustive/fuzz Release .NET 10 suite before timing. Final retained integration receives all configured Release/Debug tests plus .NET 9 and comparative corpus validation. All staging/build/test/profiling/timing work runs under the fixed host lock; temporary storage is D:\Workspaces\AI\wildcard-engine-optimization. Drivers have no database, deployment or external write paths.

## Adaptive child and setup corrections

H-014 (parent H-004): specialize only a long leading question run outside the ordinary scalar loop. H-004 improved all-question runs but consistently regressed ab?? dense runs and a?b short calls; avoid adding per-token routing to those cases. Predict a repeatable long-question gain without the observed dense/short regressions. Preserve all bounds/newline/timeout checks.

The first control harness used identical PackageId values for its distinct assemblies; the generated dependency manifest omitted one assembly. Corrected the control PackageId before any accepted measurements. A source transformation guard also detected two retry sites; narrowed the patch to the documented ordinary MatchWindow site before testing H-005. Failed setup logs are retained. Diagnostic warmup is now 10,000 calls per fixture (initial profile/control/H-004 used 100,000); timed warmup and sample policy are unchanged. Synthetic CPU_TIME leaves prevent reliable exclusive method attribution in the exported Speedscope stacks; report inclusive sampled residence only.

H-015: compare pinned read-only UTF-16 pointer indexing in MatchWindow against safe indexing; Tier1 retains range-failure edges. Both immutable strings are fixed for the entire method; each indexed access inherits the existing nonnegative token/text/end guards. No pointer escapes, writes, or speculative out-of-range loads. Predict lower scalar-loop overhead; reject if no substantial repeatable complete-call gain warrants unsafe maintenance and pinning burden. M4 candidate after safe run comparisons.

H-016: prepare immutable literal prefix/suffix offsets once in the instance constructor and pass them to ordinary MatchWindow. Sampling records repeated token searches and source confirms recomputation per reused call. Charge two added int fields, constructor scans and extra argument registers. Predict lower reused long-sparse cost; reject for materially worse construction/static/short calls. S4/R2 candidate; no invalidation because matching pattern and options are immutable.

H-017 (parent H-013): retain periodic finite-timeout checkpoints in the ASCII literal loop. H-013 showed strong long/short literal gains but its scalar loop checked elapsed time only after completion, potentially delaying cooperative cancellation on very large inputs. Add the existing MatchClock by ref and Check per iteration; predict most of the gain survives while maintaining cancellation granularity. This child supersedes the unintegrated H-013 prototype regardless of its speed.

H-018 (parent H-005): use full case-sensitive literal-segment search after stars, restricted to patterns of at least 16 units. H-005 greatly improved sparse/complex search but regressed simple calls and repeated near-miss literals. Search the entire next literal run with span IndexOf/Ordinal to avoid first-character false positives; preserve exact bounds and forbid wildcard consumption of intervening LF. A one-character segment uses the string character search. Predict sparse/complex gains without the observed simple/near-miss losses. No substring allocation or compiled metadata.

H-019 (parent H-018): hoist the immutable case-sensitive/length search-routing predicate once outside the retry loop. H-018 leaves a repeated-negative LF workload slower despite excluding its short pattern from search. Predict lower short/retry overhead without sacrificing full-segment gains; test against committed 4bc779e and preserve H-018 records.

H-020 (parent H-014): prepare the leading question-run length once for reusable instances. MatchWindow currently rescans 1024 pattern question marks per call even after H-014 grouping. This experiment uses 4bc779e plus H-014 as its contemporaneous control to isolate preparation; source identity records the different baseline. Charge one extra int and construction scan, preserve static scan/checkpoint behavior and all LF checks. Predict much lower reused question-run cost without material static/constructor harm. Final combined acceptance returns to unmodified 4bc779e as control.

H-021 (parent H-018): use segment search only when first encountering a star; leave subsequent retry transitions scalar. H-019 invariant hoisting did not resolve short/repeated-negative regressions. Sparse and all-near-miss cases obtain their main benefit from the initial segment search; removing extra retry-path routing may preserve short-call latency. Predict retained complex/sparse gains with lower short/LF overhead.

H-022 (parent H-017): normalize non-ASCII case-insensitive instance patterns at construction to avoid repeated pattern-side Unicode Fold calls. Use H-017 as contemporaneous control. Keep raw Wildcard/diagnostics, constructor-captured case groups, flags and input-side folding; a per-instance marker records prepared case state. This prototype intentionally charges both a temporary char array and retained string in construction. Predict lower reused Unicode cost; reject for substantial constructor/allocation/maintenance burden or broader case/short-call regression. No static preparation or per-match buffer.

## Final integration and stopping condition

Retain H-014/H-016/H-017/H-018/H-020 as a safe combined implementation; integration uses the original 4bc779e control and 54 unfiltered samples per engine/case/mode. Constructor allocation is 72 versus 64 bytes in every sample; default matching is zero bytes in every static/reused sample. The original 13-case equal-weight geometric mean improves 1.9% static, 2.3% reused and 0.9% construction. Large targeted gains coexist with small short-call and repeated-star regressions; raw tables and launch effects expose these. The added constant metadata and safe range/search specialization are adopted for repeated/adversarial workloads, not universal throughput superiority.

Release and Debug pass 213 tests on .NET 8/10 and 216 on .NET 11; additional .NET 9 Release passes 213. Corpus validation passes. The first integration timeout fixture became fast enough to finish within budget; use IgnoreCase for its native scalar retry workload and retain the archived failure. A disposable-layout packaging failure looked two parent levels above the flattened project; fix only staged README/LICENSE includes to one level, preserve the failed log, and re-run packing without repeating passed tests. Production project layout is unchanged. Package/symbol contents verify at version 2.0.0.

Nineteen new candidates are disposed, with four compiler/API-only effects left inconclusive and unretained. All catalogue categories are accounted for above. Prepared Unicode representation is rejected for constructor cost and proportional retained pattern storage; changing its allocation primitive would not remove that ownership burden. Unsafe, general run, interior-compare, forced-inlining and alternative routing branches are rejected. No material pending hypothesis remains within the fixed-size-state, safe-code and complete-call policy. This is a bounded local investigation, not a claim that all conceivable library/application/architecture optimization potential is exhausted. Future application frequencies, cold-start/large-memory cases or another ISA require a new evidence packet.
