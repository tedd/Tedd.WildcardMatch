# Borrowed UTF-16 API continuation

Baseline epoch: committed `0c39b9d`. The user requested span support; this is an API and ownership investigation, not another search over the previously exhausted wildcard algorithm. Historical optimization results remain unchanged. The previous fixture harness is reused with distinct control assembly identity. Temporary projects, packages, logs and traces stay under `D:\Workspaces\AI\wildcard-spans`.

Primary outcome: eliminate caller-required input/pattern materialization for borrowed slices while preserving string results, null exceptions, culture capture, newline options, timeout diagnostics, immutable pattern ownership and constant match-state memory. The shared core prevents two diverging wildcard algorithms. A reusable span-pattern constructor must copy its pattern once; borrowed inputs must not escape. Default spans mean empty text, not null strings.

## Hypotheses registered before measurement

- H-023 (M7): accepting borrowed input removes `slice.ToString()` before each reused match. Compare the complete old materialize-and-match call with direct span matching; measure nanoseconds and allocated bytes. Expected zero matching allocation and repeated latency improvement for long slices. Empty slices are a negative control. Reject any oracle/lifetime failure.
- H-024 (M7): accepting a borrowed static pattern also removes pattern `ToString()`. Compare two materializations plus old static matching with the two-span static API. Expected allocation savings proportional to both slice lengths; include short, empty, dense, Unicode, failed and newline matches. Do not infer that span matching is intrinsically faster than already-owned strings.
- H-025 (M3/R2): a single span core can preserve the optimized string engine without two algorithm implementations. Compare identical owned-string calls against the committed control across all 23 earlier fixtures. Inspect optimized native code, especially span comparison/search and the expanded stack-only timeout state. Investigate coherent regressions exceeding 15% and 5 ns across launches; this is a review trigger, not a universal adoption threshold. Shared-core maintenance and the requested span API are independent adoption benefits.
- H-026 (M1/M2): .NET 11 x-mode VT normalization can avoid a new normalized string using bounded stack scratch (maximum 512 bytes) and an ArrayPool fallback. Validate sizes 255/256/257 and all-VT patterns. Compare complete static calls on .NET 11 against the existing string normalization; measure cold pool separately from warm steady state. Pool rental may allocate and retain memory, so no universal zero-allocation promise applies to this rare mode. All initialized output is bounded and the array is returned in finally.

No additional independent algorithm, unsafe memory, UTF-8 interpretation, native ownership, asynchronous matching, caches or scheduling experiments are justified by this request. Existing coverage dispositions for CPU, storage, concurrency and unrelated memory categories remain applicable. M1/M2/M3/M7/R2 are reconsidered for new span lifetimes and scratch storage; H-023 through H-026 exhaust the initial evidence-supported mechanisms. Expand only for measured regressions or native-code evidence.

## Protocol

Build/restore, tests, warmup, timing, native-code capture and reprofile are serialized under the scientific-method-performance host lock. Local-only fixtures and scripts have no database or external write paths. Release .NET 8/10/11 independent oracle, Unicode differential and seeded fuzz suites precede timing. Debug span tests check stack and validation behavior. Preserve every failed attempt as evidence.

Default runtime tiering/PGO and workstation GC, Windows x64, SDK pinned by global.json. Bind the timing process to CPU 30. Warm every control/candidate jointly for 100 ms; calibrate common iteration counts to at least 20 ms of control work; nine alternating ABBA/BAAB blocks per case and three fresh processes. Keep all raw samples, ranges, bytes and observable checksums; subtract no harness overhead. Owned-string static/reused fixtures and construction are controls for integration burden; slice conversion is intentionally inside the timed caller because it is the removable cost. Candidate span views use guarded nonzero offsets. There is no representative application workload, so results are local complete-call measurements only.

Stop when the borrowed API and invariants pass, allocation removal is measured, the owned-string regression check has a documented disposition, normalization fallback is validated and measured, and no material evidence-derived candidate remains. Do not publish another package implicitly: the last NuGet authorization concerned the already completed 2.0.0 release.

## Evidence-derived follow-up queue (registered after initial launch 1)

Initial integration removes 4,144 bytes from long-literal sliced static calls, but existing short string matches gain roughly 8–20 ns and question/star calls also regress. Do not adopt this latency burden without testing plausible causes. Keep the initial candidate as an immutable source epoch.

- H-027 (M7/R2, parent H-025): only reusable matchers can time out, and their original patterns are already owned strings. Replace the timeout state's original-pattern span with that owned string and capture input only for finite budgets; remove the redundant original-pattern span argument from the shared core. This reduces diagnostic state/argument copying while preserving allocation-free successful finite calls and exact slice diagnostics on failure. Compare against the initial span candidate using the same complete-call fixtures; validate all timeout/null/culture/fuzz invariants before timing. Expect broad reduction in constant per-call overhead, not changes to wildcard work.
- H-028 (R2, parent H-025): if optimized native code retains the string-to-span forwarding wrapper, allow inlining only that small adapter. This can remove an extra forwarding frame while keeping null validation and the shared algorithm. Execute only if actual optimized caller code shows this call. Compare separately against H-027; do not credit both mechanisms from a combined experiment.

H-028 is not applicable: the initial optimized string caller already bypasses the string adapter and calls the span core directly.
